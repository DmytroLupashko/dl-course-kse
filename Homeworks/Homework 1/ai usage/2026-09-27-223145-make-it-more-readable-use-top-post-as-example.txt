❯ what issues thos problems had

⏺ Per the report, the flagged rows had one of two problems:

  1. Zero electricity — every electricity reading was exactly 0. Since a
     building always draws some power, a flat zero indicates a broken meter or a
     data gap, not real usage.
  2. Off when needed — steam or hot water read 0 for a week or more while that
     week's average temperature was below 10 °C, or chilled water read 0 while
     the average was above 20 °C. In both cases the system should have been
     running given the weather, so a sustained zero signals a broken/missing
     reading rather than the building genuinely using no energy.

❯ what 2nd means?

⏺ The second rule ("off when needed") flags heating/cooling meters that stay at
  0 during weather when they logically should be running:

  - Steam or hot water reading 0 for at least 7 consecutive days, during a week
    whose average outdoor temperature is below 10 °C. Below that temperature, a
    building would normally need heating, so a full week of zero heating
    readings is implausible — it means the meter broke or data is missing, not
    that heating was truly off.
  - Chilled water reading 0 for at least 7 consecutive days, during a week whose
    average outdoor temperature is above 20 °C. Above that temperature, cooling
    would normally be running, so the same logic applies in reverse.

  So it's not "any single zero reading" — it's a sustained week-long streak of
  zeros paired with weather that makes that streak physically unlikely.

❯ What is the idea if this paragraph?

⏺ This paragraph is explaining a check the team ran to see if train and test
  data differ in a way that would let the model "cheat" or that they'd need to
  fix — adversarial validation.

  The method: train a classifier whose job is just to distinguish training rows
  (2016) from test rows (2017–2018). If that classifier can do this easily (high
  AUC), it means some feature encodes a train/test split, which is dangerous —
  the model could be relying on that spurious signal instead of genuinely
  learning to predict energy use, and you'd normally want to drop that feature.

  Here they found:
  - Using all features, the classifier gets AUC 0.75 — seemingly it can tell
    train from test.
  - But drop weather entirely and it falls to 0.52 (basically random) — so
    weather is the thing driving that separability.
  - Yet each individual weather feature alone only gets 0.51–0.54 (also
    near-random).

  The conclusion: no single weather feature leaks train/test identity, but the
  combination of weather values effectively acts like a timestamp fingerprint
  (i.e., "this exact combination of temperature/pressure/wind only occurred in
  this one hour of this one year"). That's not a generalizable pattern a model
  could learn to exploit for predicting the target — it's just an artifact of
  weather being unique per hour. So despite the AUC 0.75, there's no actual
  feature to remove; the "leak" isn't exploitable/learnable, so they keep all
  features.

  That's the idea.

❯ Explain how mlp 4out embening model is designed: what it takes as input, what
  it outputs

⏺ mlp_4out_emb is MeterMLP(n_features=33, n_buildings=1449) in modeling.py
  (ashrae/modeling.py). It predicts one row, meaning one building × one meter ×
  one hour.

  Input: three things per row

  1. x: 33 numbers, built by build_features in features.py (ashrae/features.py)
     and standardized with a scaler fitted on the training rows:

  | Group        | Features
                                  | Count |
  |--------------|--------------------------------------------------------------
  ---------------------------------|-------|
  | Building     | log1p(square_feet), year_built (filled with the training
  median), a "year_built missing" flag | 3     |
  | Weather      | air temperature, dew temperature, sea-level pressure, wind
  speed, wind direction as sin/cos   | 6     |
  | Time (local) | hour sin/cos, day of week sin/cos
                                  | 4     |
  | Meter type   | one-hot: electricity, chilled water, steam, hot water
                                  | 4     |
  | Building use | one-hot primary_use (Education, Office, …)
                                  | 16    |

  2. building: the building id (0–1448), used to look up that building's
     embedding.
  3. meter: the meter type (0–3), used to pick which output to keep.

  Inside

  building id ──► Embedding(1449 × 16) ──► 16 learned numbers ─┐
                                                               ├─► concat: 49
  numbers
  x (33 features) ─────────────────────────────────────────────┘
        │
        ▼
  Linear 49→64 ─► BatchNorm ─► ReLU
  Linear 64→64 ─► BatchNorm ─► ReLU
  Linear 64→4    (one output per meter type)
        │
        ▼
  keep the output of the row's own meter ─► 1 number

  - The embedding is a learned table with 16 numbers per building. It starts
    random and is trained with the rest of the network. It lets the model learn
    what size, use and weather can't explain: why two similar buildings differ
    in consumption by orders of magnitude, and how each one reacts to weather.
    It holds 23,184 of the model's 31,060 parameters.
  - The 4 outputs give each meter type its own final layer on top of shared
    hidden layers. Heating and cooling react to temperature in opposite
    directions, so they need separate outputs. Each row trains only the output
    of its own meter (gather).
  - The meter type goes in twice: as the one-hot in x, so the hidden layers know
    it, and as the index that picks the output.

  Output

  One number per row: the predicted log1p(meter_reading).

  - Training: MSE between this number and the true log1p(reading), which is
    exactly RMSLE squared.
  - Validation: negative predictions are clipped to 0, since readings can't be
    negative.
  - Submission: expm1 turns it back into a reading. Site 0 electricity is then
    converted back from kWh to kBTU, the unit Kaggle scores it in.

  A building the model never saw in training would keep its random, untrained
  embedding. That doesn't happen here, since all 1,449 buildings appear in 2016.
